DSH-SUPERAGENT · ARCHITECTURE OVERVIEW

超级 Agent 的
架构全景

一个面向单个仓库的主动式编码 agent。它从 Feishu 消息与 GitHub 事件中接单，在自己的 Session 与目录里完成工作，最后把可评审的 Pull Request 交回给人。

查看系统全景 浏览领域模型

Design principle

Take as little human attention as possible, and give as much value as possible.

尽量少占用人的注意力，尽量多交付价值。

  • 被请求或书面规则允许时才行动
  • 只在有结果、需要决策或无法完成时说话
  • 先成为可评审的 PR，由人决定是否合并

02 / FLOWS

三条路径，一套边界

明确请求、订阅后续与主动候选走不同的准入路径，但都汇入同一套 Engine 规则与工单生命周期。

新请求：从一条消息到一次可评审的交付

当名单内的人直接点名 agent，Source 只负责把事件带进来；接单、授权、派工与确认在同一个事务里完成。

  1. 01
    Source进入领域

    接入与过滤

    Feishu 点名或 GitHub Issue 指向 agent。Source 丢弃自己的消息、读取窗口之外的事件，把其余事件作为 Trigger 幂等落库。

  2. 02
    EvalGate

    确定性准入

    Gate 检查发送者、Source 的允许名单与 Thread 上下文。被允许的人明确点名即成为 explicit 候选，无需模型研判；其余情况进入评估或直接记录忽略。

  3. 03
    Decisionaccept

    接单并授予 Mandate

    主 Session 用 orchestrator_route 接受。Engine 在同一事务里创建 Ticket、Mandate、首个 Assignment、Thread 订阅与确认消息。

  4. 04
    Executorlaunch

    准备目录，启动 Worker

    launch 副作用运行 prepare 命令并创建 worker-<ticket id> Session。首条消息带工单标题、任务文本、来源卡片与授权边界。

  5. 05
    Workerwork → PR

    实现、验证、交付

    Worker 在自己的目录里完成改动、自审并运行相关检查，然后推送分支、打开 PR。PR 被绑定为工单的 Thread；报告 ready 表示等待评审。

  6. 06
    Channelresult

    写回原对话，等人合并

    主 Session 把结果与 PR 链接发回请求所在对话。人评审并合并；PR 关闭后，工单在所有跟踪的 PR 结束后以 merged / closed 收尾，并保留订阅以便后续消息恢复。

    在这个部署里，agent 不自行合并；没有指定 merge CLI 时，由人合并 PR。
接单的原子性是关键：Ticket、Mandate、Assignment、确认消息要么一起出现，要么都不出现。重放同一个 Trigger 不会产生第二张工单。

后续消息：订阅扇出，不重新授权

对话一旦与工单绑定，之后的消息会直接到达该工单；它携带上下文，但不自动扩大授权范围。

  1. 01
    Subscriptionfan-out

    消息直达工单

    Thread 上的新消息（包括 bot 与 CI）会扇出到所有仍在订阅的工单，不经过 Gate。订阅只传递上下文，授予新权限的仍是 Mandate。

  2. 02
    Ownershipno Eval

    由 Executor 判断归属

    人的消息到达工单后由该工单的 Executor 决定：在范围内就继续执行；超出范围或属于另一张工单，则交回一次，等没有其他工单拥有它时再进入新的 Eval。

  3. 03
    Inputdelivery

    作为 Input 投递

    消息被渲染成 Input，按顺序投递给运行中的 Assignment。人直接写消息可以多用一槽，优先于新的启动，保证已有工作不被新任务挡住。

  4. 04
    Lifecycleresume

    结束后仍可恢复

    已结束的工单保留订阅。人的消息可以按原 Mandate 恢复它，但恢复前要按当前 Policy 重校验；被明确 stop 的工单不再接收任何消息。

    工单结束时，未被确认、回答或交回的消息会回到 Eval；已读但没有后续动作的消息（例如感谢）不会。

主动工作：先研判，再接受

未点名消息、bot 消息或名单外成员的请求按准入规则与 accept mode 处理；bot 使用 Source 的 bot 名单。默认 observe，只记录“会接受”，不真正开工。

  1. 01
    Admissioninferred

    形成推断候选

    Gate 依据接收范围、是否点名与 Source 的 bot 名单给出 inferred 强度；accept mode 为 off 时推断工作完全不进入候选。

  2. 02
    Assessmentorchestrator_eval

    模型研判意图

    主 Session 读取有界的 Thread 上下文、相关工单与当前 Policy，对每条启用规则逐一判断是否匹配，并给出意图证据。

  3. 03
    Modeobserve / auto

    接受或记录

    auto 模式下，满足规则的正面判断可直接接单；observe 模式把它记录为 “would accept”；无规则匹配则忽略。每次判断都绑定当时的 Policy 版本。

  4. 04
    Mandaterules

    把规则带进工单

    命中的规则写入 Mandate，Executor 收到规则名称与限制。规则可以覆盖默认的流程与沟通要求，例如静默、指定评审人、合并前审批。

    只有人的 stop 才撤回 Mandate；Policy 变更会重排评估并通知受影响工单，但不撤销 Mandate，也不取消正在执行的工单。
03 / DOMAIN

十一个概念，各自守住一条规则

Source、Thread、Eval、Mandate 与 Subscription 构成核心；其余概念围绕授权与执行。代码、工具、面板与文档都只说这些词。

Source来源

事件流

一种可复用的 kind，加一份实例配置：是否运行、监听什么。它知道如何把外部事件翻译成 Trigger。

规则：保存读取位置与自己的 bot 身份；重启不重放事件。
Trigger触发

不可变事件

一次事件及其 Source 元数据，例如发起者。它是审计与幂等的单位。

规则：归属于一个或多个 Thread；同一个 Trigger 接受两次只产生一张工单。
Thread线程

按时间排列的对话

由 Source 定义哪些 Trigger 属于同一条 Thread。它持有订阅、运行中的 Eval 与 Decision 历史。

规则：同一时刻最多一个 Eval；一条 Thread 可以有多张工单。
Correlation关联

Thread 之间的关系

同一个 Trigger 出现在多条 Thread 上时产生的联系，用来补充上下文。

规则：只添加上下文，永远不负责路由。
Channel渠道

Thread 的写侧

Source 定义可回复的地址；一条 Thread 可以有多个 Channel，一张工单持有一组。

规则：确认、回答、PR 与已解决的 review 都是 Channel 写入。
Policy策略

版本化的授权规则

研判规则、accept mode，以及每个 Source 的部分：谁可以发起、bot 名单、admission table。

规则：规则变更会重排 Eval；影响工单的变更会送达其 Assignment，但不撤销 Mandate。
Eval评估

两层研判

Gate 做确定性准入，Assessment 让模型按规则判断意图；输出一个 Decision。

规则：无状态；输入是 Trigger 批次、Thread 快照、全部相关工单与当前 Policy。
Mandate授权

接受时授予的范围

记录 Policy 版本、范围、强度、命中规则、发送者身份与准入路径。

规则：不可变。只有人的 stop 能撤回，或重校验失败时失效；扩大范围要新工单。
Ticket工单

授权工作的单位

引用 Mandate，持有 Channel、Input 与 Assignment；定义自己的 open / ended 状态。

规则：只有 Eval 能创建；人的消息可以恢复已结束工单，除非被 stop。
Assignment派工

工单与执行器的绑定

一张工单先后可以有多个 Assignment；执行器在领域之外，通过它连接进来。

规则：pending → running → ended，独立于工单；只有最终报告能从执行器一侧结束工单。
Subscription订阅

工单与 Thread 的多对多关系

由 Thread 持有。匹配的消息扇出到每张在线工单，不检查发送者。

规则：已结束工单保留订阅；bot 与 CI 不唤醒它。
人不是领域概念Trigger 只携带 Source 给出的发起者标识。允许名单是 Source 的 Policy 部分；同一个人在不同 Source 上的账号，是 agent 阅读的提示文本，而不是实体映射。
执行器在领域之外Executor 的 Session、目录与进程不属于领域模型，只通过 Assignment 与工单相连。这样工单可以换执行器、被恢复或被多次派工。
设计里刻意没有的东西
Principal / Membership 实体人是 Trigger 元数据；跨 Source 的身份映射只是提示文本。
“追加到工单”的 Decision追加剧是订阅扇出，不需要 Eval。
Eval 自己等待需要等待的条件属于 Source；Eval 不反向依赖 Source。
每条 Thread 最多一张工单一条 Thread 可以承载多项独立工作，由研判避免重复。
Ticket 状态跟随 DSH Session工单可被移交、恢复或多个 Executor 执行，必须自己定义状态。
Policy 变更时取消运行中工单取消会留下半成品；变更被记录并送达，而不是撤回授权。
04 / LIFECYCLE

工单此刻在等谁

每张打开的工单只有一个阶段，由它在等待的东西决定。从上往下读，第一个匹配的行生效；person 阶段意味着缺少人的输入就无法继续。

person / deliveryInput 投递失败，2 秒后重试，随后指数退避至 1 分钟输入未送达
person / answer工单上有一个结构化的 Attention等待回答
person / review最新报告是 ready等待评审
person / blocked · failed最新报告是 blocked 或 failed，且此后没有人的消息到达受阻 · 失败
working / queued没有 Assignment，或 Assignment 仍为 pending排队中
idle最新报告是 waiting，或 Assignment 已结束等待触发
working其余情况执行中

人的新消息会释放 blocked / failed 工单；空闲工单等待订阅 Thread 上的触发器，而不是轮询。

工单如何结束

结束由事实决定，而不是由 Executor 自称完成。

  • completed没有 PR 的工作报告 ready，直接完成。
  • dropped没有需要人处理的工作，例如无法复现或已被取代；通常不发消息。
  • merged跟踪的 PR 全部结束，且最后一次关闭是合并。
  • closed跟踪的 PR 全部结束，最后一次关闭不是合并。
  • stopped人明确停止，Mandate 撤回，工单不再接收任何消息。
progress waiting ready blocked failed dropped

失败、恢复与暂停

工单状态来自存储的事实，所以重启后仍然成立。

  • blocked / failed暂停自动 Input，但工具仍可用；人可以直接在 Session 里继续。
  • retry在同一 Session、目录、分支与 PR 上开始新的 Assignment。
  • restart中断的 Assignment 带恢复说明重启；等待、就绪、受阻或失败的报告保持原状。
  • pause暂停派工、新 Eval、投递与回复；已在进行的 turn 不被打断。
  • resume人的消息按当前 Policy 重校验 Mandate；通过后恢复，失败则消息回到 Eval。
